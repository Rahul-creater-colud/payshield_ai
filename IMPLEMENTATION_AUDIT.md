# PayShield AI Implementation Audit

## Scope and trust boundaries

This audit describes the current checked-in workspace implementation. PayShield is a local hackathon prototype: it analyzes records submitted to its own API and does not connect to NPCI, a bank, a payment provider, or a live UPI network. It cannot stop or reverse payments. Stored seed/catalog and screen mock fixtures are synthetic and are labeled as demo data; the API does not silently substitute fixtures when LIVE requests fail.

The final transaction risk category is produced by deterministic heuristics. The optional Random Forest is a separate estimate trained on labels generated by a hand-authored formula. Its evaluation is a synthetic-label agreement measurement, not evidence of real-world fraud performance, and it does not change the final heuristic decision.

## Data storage and statistics

The FastAPI application uses SQLAlchemy with SQLite. Starting the backend from `backend/` stores data in `backend/payshield.db` unless `DATABASE_URL` is overridden. Startup creates missing tables and does not automatically seed generated transactions. The demo seed/reset command is a separate, destructive operation.

Dashboard metrics are derived from persisted transaction, assessment, and payment-event records. Safe/suspicious values describe PayShield classifications; internally recommended review/stop outcomes are not provider blocks. Provider-blocked counts require verified, non-simulated payment events. Fraud-prevented monetary value is unavailable (`null`) because no verified prevention records or defensible calculation support it.

The checked-in ML dataset is generated by `ml_model/ml_model/create_dataset.py` using a hand-authored risk formula. The training report and metrics must be read with that provenance; they do not establish effectiveness against real UPI fraud.

## Security and operational limitations

- Grievance, intelligence, and some administrative routes do not implement user authentication/authorization. They are suitable only for isolated local demonstrations, not deployment on a public/shared network.
- Rate limiting and a production access-control model are not implemented. The destructive admin reset is disabled by default; keep `ENABLE_ADMIN=false` outside isolated demonstrations.
- Do not load untrusted serialized model artifacts. Pickle/joblib artifacts can execute code when loaded.
- No UPI PIN, OTP, password, or payment credential is required or collected.
- URL analysis is intentionally static and does not make outbound requests.
- No real bank/provider integration, payment execution/blocking, collect-request monitoring, OCR, independently verified merchant registry, or live threat-intelligence feed is present.

## Run locally

Backend PowerShell:

```powershell
Set-Location 'D:\MNIT hack\backend'
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload --host 127.0.0.1 --port 8000
```

Frontend in a second PowerShell:

```powershell
Set-Location 'D:\MNIT hack\upi-fraud-shield'
npm install
$env:VITE_API_BASE_URL = 'http://127.0.0.1:8000'
npm run dev -- --host 127.0.0.1
```

Open `http://localhost:5173`. The frontend defaults to the same API URL; `VITE_API_BASE_URL` can override it. The API docs are available at `http://127.0.0.1:8000/docs`.
