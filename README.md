# PayShield AI / UPI Fraud Shield

PayShield is a local prototype for heuristic risk assessment of transaction records submitted to the application. It is not connected to NPCI, a bank, or a payment provider, and cannot monitor or block real UPI payments. An optional experimental Random Forest reports a supplemental estimate from a synthetic-trained model; it does not change the heuristic verdict and has no real-world validation or accuracy claim.

## Architecture and data

- **Frontend:** React 18, Vite, Tailwind CSS, and Recharts in `upi-fraud-shield/`.
- **Backend:** FastAPI and SQLAlchemy in `backend/`.
- **Storage:** SQLite at `backend/payshield.db` when the backend is started from `backend/`.
- **Data:** The checked-in/current database and UI mock fixtures contain synthetic data. Backend responses identify this as `DEMO / SYNTHETIC DATA`. Starting with no database creates an empty database; no seed data is loaded automatically.
- **Demo mode:** The frontend's explicit MOCK mode uses static/in-memory demo fixtures, clearly labeled as demo. LIVE mode calls FastAPI and does not fall back to those fixtures on errors.

## Screens

The fraud-operations workspace includes Dashboard, Transaction Risk Checker, Collect Request Protection, Fraud Analytics & Model Status, Fraud Network, Merchant Verification (local catalog lookup only), Fraud Intelligence & Grievance Centre, Suspicious URL Scanner, Transaction History, Alerts & Risk Report, and the retained Evidence Scanner.

The UI follows the Stitch project's Inter / navy / teal visual system. Analytics use stored records and heuristic assessments; validated model evaluation, fraud-prevention value, real merchant verification, live collect-request monitoring, and payment-provider blocking remain unavailable unless an authorized, verified integration is added.

## Run locally

Backend (from a PowerShell terminal; the model dependencies are included):

```powershell
cd backend
python -m pip install -r requirements.txt
python -m uvicorn app.main:app --reload --port 8000
```

Frontend (from another terminal):

```powershell
cd upi-fraud-shield
npm install
npm run dev
```

Open `http://localhost:5173`. The frontend `.env.example` sets `VITE_API_BASE_URL=http://127.0.0.1:8000`; copy it to `.env` in `upi-fraud-shield/` for a fresh checkout. FastAPI docs are at `http://127.0.0.1:8000/docs`; health is `http://127.0.0.1:8000/api/v1/health`. FastAPI CORS allows `http://localhost:5173` and `http://127.0.0.1:5173`.

The backend prefers `ml_model/ml_model/artifacts/best_model.joblib` and `best_threshold.joblib`, with support for the legacy `.pkl` artifact pair. Set `ML_MODEL_DIR` if trusted local artifacts are elsewhere, or `ML_MODEL_ENABLED=false` to disable inference. Health reports the actual model status. Missing dependencies/artifacts do not prevent heuristic assessments, but the model estimate is shown as unavailable. The training data is synthetic and its labels are generated by a hand-authored risk formula; model probabilities and evaluation metrics do not represent real-world fraud performance.

To reproduce the candidate comparison and evaluation from the checked-in synthetic dataset, run from the project root:

```powershell
python ml_model\ml_model\train_pipeline.py
```

The script compares balanced Logistic Regression and Random Forest pipelines, uses stratified train/validation/holdout splits, fits median imputation only on training data, selects the model and threshold on validation data, then evaluates once on the untouched holdout. It writes the model package, threshold, `evaluation.json`, and split CSVs under `ml_model/ml_model/artifacts/`. On the current generated dataset (10,000 rows; 8,619 negative and 1,381 generated-positive labels; no missing feature values), the selected balanced Random Forest achieved holdout precision **0.3636**, recall **0.4928**, F1 **0.4185**, and PR-AUC **0.3249** at threshold **0.3382**. Confusion matrix (negative/positive label order): `[[1486, 238], [140, 136]]`. These metrics measure agreement with labels generated by a hand-authored formula only—not evidence of live fraud detection quality.

Do not run `python -m app.db.reset` against a database you want to preserve: it drops and recreates the SQLite data using synthetic seed records. For an empty-database test, use an isolated test database or back up the existing database first.

## Synthetic demo-data enrichment and seed

The root-level enrichment scripts keep the source ML CSV unchanged and write a separate `DEMO DATA` CSV to `ml_model/ml_model/data/enriched_indian_upi_fraud_data.csv`. The deterministic enrichment normalizes coordinates to Indian cities, emits unique 10-digit phone values labeled `SYNTHETIC`, converts `TransactionFrequency` into integer `txn_per_day`, and rebalances the combined dataset and scenarios to a configurable fraud rate (2.5% by default). It also includes explicit labels for fake collect requests, mule-network transfers, night-risk patterns, and genuine new-recipient false positives. CSV scenarios use `COLLECT`; when seeded, that maps to the backend's existing canonical `COLLECT_REQUEST` enum without changing its schema.

Run from the project root to add or update the reserved synthetic records in the configured local database (`DB_URL`, defaulting to `backend/payshield.db`):

```powershell
python scripts\enrich_and_seed.py
python scripts\verify_seed.py
```

The seed is idempotent and does not change the database schema. `--reset` deletes only the seeder's reserved `CSV_`/`DEMO_` records before rebuilding them; it does not reset unrelated application data. Use `--fraud-rate 0.02` to choose another supported target rate, or `--database-url "sqlite:///C:/path/to/test.db"` to seed an isolated database. Four scenario definitions live in `data/scenarios/`: fake COLLECT, mule network, unmatched fake screenshot (PENDING), and a genuine new-recipient MEDIUM alert with a grievance. Merchant payment events are simulated only; these fixtures do not represent live UPI or bank integrations.

## Live-mode endpoints

The dashboard uses:

- `GET /api/v1/health` — local backend/database status, heuristic engine, synthetic-data labeling, and experimental-model availability.
- `GET /api/v1/fraud/analytics` — stored-row totals are separate from assessed counts. Risk counts, assessment rates, daily activity, and score distributions use persisted assessments only; imported synthetic labels are not treated as PayShield decisions. Fraud/safe outcome rates remain unavailable (`null`) because no verified outcome labels exist. Verified provider-block events are counted separately.
- `GET /api/v1/transactions` and `GET /api/v1/transactions/{id}` — persisted records and latest risk decisions.
- `GET /api/v1/fraud/alerts` — alerts derived from stored medium/high assessments.
- `GET /api/catalog` — synthetic local account references used by Merchant Verification; this does not verify merchants externally.
- `GET /api/accounts/{account_id}/network` — stored account graph and heuristic patterns.
- `GET /api/intelligence` and `POST /api/intelligence/report` — locally stored indicator records.
- `GET /api/grievances`, `POST /api/grievances`, and `PATCH /api/grievances/{case_id}` — locally persisted prototype grievance workflow with validated status transitions, not an official complaint channel.
- `POST /api/grievances/{case_id}/appeals` and `GET /api/grievances/{case_id}/appeals` — persist and retrieve local appeals for resolved/rejected cases; not an external escalation.
- `GET /api/risk/assessments` — stored assessments available to the grievance workflow.
- `POST /api/urls/scan` — static URL analysis; it does not visit the submitted URL.
- `POST /api/merchant/sessions` — creates a persisted local expected-amount ledger session.
- `GET /api/merchant/transactions/{reference}` — retrieves the locally stored demo transaction by reference.
- `POST /api/payments/simulate-callback` — records an explicitly simulated callback after validating session, merchant, amount, and duplicate references; this is not provider confirmation and does not count as a real payment event.

Analysis uses `POST /api/v1/fraud/analyze`; it records an internal risk assessment and returns a supplemental experimental ML estimate when the local artifacts and dependencies are available. That estimate does not affect the heuristic score, and the endpoint does not execute or block a payment. Gemini explanations are optional; when configured, only the score, category, transaction type, and sanitized trigger codes are sent—never transaction identifiers, amounts, free text, URLs, PINs, or OTPs. Deterministic local guidance clearly identifies when Gemini is not configured or inference fails. Collect-request control is unavailable without an authorized provider integration. Uploaded-image OCR is unavailable; only explicitly labeled synthetic sample responses exist. Fraud-prevented monetary value is not available because no verified prevention events support that metric. Deprecated `/api/v1/demo/...` routes now alias persisted records and do not fabricate fallback transactions or analytics; frontend MOCK fixtures remain explicitly labeled synthetic demo data.
